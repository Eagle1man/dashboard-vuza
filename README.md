# Дашборд ректора — локальная система вопросов по документам

Южный университет (ИУБиП) / Southern University (IMBL).
Работает целиком на компьютере, без интернета и без облачных сервисов.

---

## Что это

Дашборд с управленческой аналитикой и ИИ-ассистент, который отвечает
на вопросы **по документам университета** — положениям, протоколам,
приказам, отчётам — и показывает, из каких документов взят каждый ответ.

Три слоя данных, и их важно не путать:

| Что | Откуда данные | Статус |
|---|---|---|
| 20 показателей ленты | отчёт о самообследовании на 01.04.2026, план ФХД на 2026 год | **настоящие**, с источником и страницей |
| Мониторинг эффективности | monitoring.miccedu.ru, карточка id=1971 | **настоящие**, с датой выпуска |
| Ответы ИИ и список источников | реальные файлы из `knowledge/` | **настоящие** |

Каждый показатель подписан источником прямо на карточке, и у него
**нет исторического ряда**: документ даёт значение на одну дату, значит
сравнивать с прошлым периодом не с чем. Придумывать одиннадцать
прошлых месяцев нельзя — ровный график ректор прочтёт как историю.

Демонстрационных значений и документов в проекте больше нет: число без
документа выглядело настоящим, и подписать его было нечем.

## Быстрый старт

```
1. Двойной клик по install.bat     один раз, 3–5 минут
2. Двойной клик по start.bat       запуск
3. Открыть в Ollama нужную модель  см. раздел «Что сделать, если ИИ молчит»
```

Дашборд откроется на `http://127.0.0.1:8765/`.

> Открывать `web/index.html` двойным кликом можно — дашборд покажет
> значения из документов, но ИИ не заработает: браузер из режима `file://`
> не пускает страницу обращаться к локальному серверу. Правильный
> способ — `start.bat`.

### Как добавить документы

1. Положить файлы (PDF, DOCX, XLSX, MD, TXT, HTML) в папку `knowledge/`.
2. Запустить `start.bat` — новые файлы проиндексируются автоматически.

Папка `knowledge/` — единственный корпус: реальные файлы кладутся в
корень или в подпапку с названием подразделения. Ассистент ищет только
по ним, и каждое число в ответе подписано документом.

### Синхронизация мониторинга

Карточка ИУБиП на `monitoring.miccedu.ru` обновляется сторожем:

```
sync_monitoring.bat                         проверить и обновить
sync_monitoring.bat --check                 только проверить (код 1 — есть изменения)
sync_monitoring.bat --full                  пересобрать все 38 карточек региона
sync_monitoring.bat --watch --interval 86400   следить постоянно
```

Что делает сторож:

1. Сравнивает дату обновления на сайте и отпечаток данных карточки с
   прошлым запуском. Если ничего не изменилось — не пишет файлы.
2. При изменении обновляет JSON и markdown карточки, строку ИУБиП в
   `region_indicators.json`, пересобирает `data/monitoring.json` и
   `data/analytics.db`.
3. При новом выпуске или смене даты обновления на сайте делает полный
   обход всех 38 карточек региона — иначе места и перцентили остались бы
   от старого выпуска.
4. Обновляет индекс `knowledge`, если Ollama и модель эмбеддингов
   доступны. Если нет — JSON обновляются, а индекс догоняет при
   следующем запуске; подменять настоящие векторы заглушкой сторож не
   пытается.
5. Перед перезаписью складывает копию в `data/backup/monitoring-*`.
   Состояние проверки — `data/monitoring_sync.json` (локальное, в git не
   попадает).

#### СПО

Карточка СПО (id=1971, 20 показателей) синхронизируется отдельно:

```
sync_monitoring.bat --spo                 проверить и обновить строку ИУБиП
sync_monitoring.bat --spo --check         только проверить
sync_monitoring.bat --spo --full          пересобрать все 142 карточки СПО региона
```

Быстрый режим берёт места и медианы из `source/spo_region.json` — это
сохранённые карточки всех организаций СПО области. Если файла нет,
сторож сам делает полный обход. Полный обход стоит 142 запроса,
поэтому его стоит вынести в отдельную задачу, например раз в неделю:

```
schtasks /Create /SC WEEKLY /TN "Rector SPO sync" ^
  /TR "\"C:\Users\diorl\.cline\data\workspaces\chat\rector-dashboard\sync_monitoring.bat\" --spo --full" ^
  /ST 06:30
```

СПО и ВО — разные наборы данных, поэтому `--spo` запускается отдельно
от обычной синхронизации; состояние хранится в том же
`data/monitoring_sync.json`, но в отдельном разделе `spo`.

Автозапуск раз в сутки в Планировщике заданий Windows:

```
schtasks /Create /SC DAILY /TN "Rector monitoring sync" ^
  /TR "\"C:\Users\diorl\.cline\data\workspaces\chat\rector-dashboard\sync_monitoring.bat\"" ^
  /ST 06:00
```

### Резервная копия

`backup.bat` — копирует `data/dashboard.db` в `data/backup/`, хранит 30 копий.
Вся система — один файл, копия файла и есть копия системы.

## Реальная структура университета

Название, подразделения и образовательные программы — не вымышленные.
Они взяты с официального сайта ЧОУ ВО «Южный университет (ИУБиП)» на
момент подготовки дашборда:

| Что | Источник |
|---|---|
| Название и форма собственности | `sveden/struct/` — ЧОУ ВО «Южный университет (ИУБиП)» |
| Академии и кафедры | организационная структура на 2026–2027 учебный год, приложение 1 к приказу; принадлежность кафедр академиям — страница «Академии» на сайте |
| Образовательные программы и годы редакций ФГОС | `sveden/eduStandarts/` |
| Состав опросов внутренней оценки качества | `sveden/vnoko/` |

Структура — **5 академий и 9 кафедр**:

| Академия | Кафедры |
|---|---|
| Академия экономики, туризма и индустрии гостеприимства | Финансы, бухучет и налогообложение · Экономика, туризм и инновационные рыночные исследования |
| Академия управления и цифрового развития | Управление организационными системами · Информационные технологии и прикладная математика |
| Академия права и государственной службы | Государственно-правовые · Гражданско-правовые · Уголовно-правовые дисциплины |
| Академия гуманитарных технологий | Психология и управление персоналом · Гуманитарные дисциплины |
| Академия профессионального образования | кафедр из этого списка не имеет — она про среднее профессиональное образование |

Три документа о структуре расходятся между собой, и это не ошибка
документов, а разные моменты времени:

- **организационная структура на 2026–2027 учебный год** (приложение
  1 к приказу) — действующий документ, 5 академий и 9 кафедр;
- **отчёт о самообследовании на 01.04.2026** (стр. 10) — на 1 апреля
  2026 академий было тоже пять, но назывались они иначе, а кафедр было
  на две больше: «Физическое воспитание» и «Экономика и инновационные
  рыночные исследования»;
- **страница «Академии» на сайте** — принадлежность кафедр академиям
  указана прямо, но «Физическое воспитание» на странице ещё стоит:
  страница не обновлена под текущий приказ.

За составом кафедр идём по приказу, за принадлежностью — по сайту.
Академия профессионального образования в сводке остаётся: без неё
структура выглядит неполной.

Блоки дашборда — семь, по зонам ответственности проректоров:
академическая политика, учебные результаты, финансово-хозяйственная
деятельность, качество образования (ВНОКО), наука и метакомпетенции,
воспитательная работа и молодёжная политика, цифровые сервисы и ЭИОС.

### Справочник образовательных программ

`dim_standard` хранит 25 программ: 8 бакалавриата, 6 магистратуры,
11 среднего профессионального образования. По каждой — код, название,
уровень, год утверждения действующей редакции и год последнего
изменения. Год изменения — живой сигнал: по нему видно, где стандарт
устарел и требует пересмотра. Стандарты, не менявшиеся более трёх лет,
помечаются значком ⚠ в интерфейсе.

**Чего в справочнике нет и почему.** Численность обучающихся по каждой
программе на сайте не публикуется. Заполнять её вымышленными числами
нельзя: ректор примет их за реальные данные. Поэтому справочник —
это состав и версии программ, а не контингент по ним.

## Логотип

`web/img/iubip-logo.svg` — официальный знак университета. Канонический
источник: <https://github.com/Eagle1man/iubip-sbp-pay> (`assets/iubip-logo.svg`).
Копия здесь лежит без правок.

Что важно знать при доработках:

- в файле **нет элементов `<text>`**, все буквы — контуры. Логотип не
  зависит от того, какие шрифты установлены на компьютере. Добавлять
  текст в SVG нельзя: прежние версии рисовали монограмму шрифтом Georgia,
  и на машине без него знак рассыпался;
- пропорции знака **121 : 74**, а монограмма выходит за нижний край
  глобуса. В стилях задана только высота, ширина считается сама
  (`width: auto`). Если задать ширину и высоту одновременно, знак
  растянется по диагонали;
- в знаке есть контур, залитый белым — это подложка под красными
  буквами. На белом фоне она не видна, на сероватом проступает ореолом.
  Поэтому в шапке фон чисто белый, а в тёмной теме логотип скрывается:
  синий знак на тёмном нечитаем, а перекрашивать официальный знак без
  разрешения нельзя.

## Что где лежит

```
data/dashboard.db      всё состояние: цифры, документы, векторы, история
knowledge/             документы для поиска (ваши файлы)
web/                   интерфейс (HTML/CSS/JS, без сборки)
backend/               сервер, поиск, ИИ
logs/                  журналы
```

### Устройство базы

Один файл SQLite, четыре слоя:

| Слой | Таблицы | Зачем |
|---|---|---|
| Справочники | `dim_metric`, `metric_alias`, `dim_org`, `dim_period`, `dim_standard` | что измеряем, как это ещё называется, какие есть образовательные программы |
| Витрина | `fact_metric`, `fact_detail` | цифры по периодам и подразделениям |
| Корпус | `doc`, `doc_chunk`, `chunk_fts`, `chunk_vec` | документы, куски, полнотекст, векторы |
| Журнал | `ask_log`, `meta` | история вопросов, настройки |

**Почему SQLite, а не PostgreSQL.** База на 32 метрики и сотни документов
не требует отдельной службы, пользователя, пароля и обновлений. Один файл
копируется на флешку — это и есть резервная копия. Полнотекстовый поиск
(FTS5) входит в SQLite, поэтому вторую базу ставить не нужно.

**Почему векторы хранятся в том же файле.** При корпусе вуза
(5–9 тысяч кусков) полный перебор косинуса занимает единицы миллисекунд,
поэтому отдельный векторный сервер не нужен. Он понадобится, только
если корпус вырастет до десятков тысяч кусков.

## Архитектуры поиска

Пять архитектур RAG закрывают пять разных способов сломаться. Ниже
что реально сделано и почему именно так.

| Архитектура | Состояние | Закрывает |
|---|---|---|
| Гибридная | **готово и проверено** | пропущенные ключевые слова |
| Агентная | **готова** | вопросы, требующие нескольких источников |
| Корректирующая | **готова** | ненадёжный поиск |
| Граф ссылок (вместо полного GraphRAG) | **готов** | недостающие связи |
| Мультимодальная | **готова частично** | знания в графике |

### Гибридная — слова и смысл одновременно

`retrieve.py`: FTS5 по словам с русским стеммингом, векторы Ollama,
слияние RRF, переранжирование по покрытию с весами по полям
(название 3, заголовок 2, текст 1).

Что оказалось важным, когда это заработало:

- **оба канала обрезаются до одинаковой длины до слияния.** Канал,
  вернувший больше записей, иначе выигрывает за счёт количества и
  топит точность другого;
- **канал-вектор отключается, если модель не скачана.** Эмбеддинг-заглушка
  не несёт смысла, но с половинным весом он перемешивает выдачу;
- **порог схожести.** Если ни один фрагмент не близок к вопросу,
  честно вернуть пусто, а не подсунуть нерелевантное.

### Корректирующая — оценка контекста до генерации

`retrieval_judge.py`. Базовый RAG берёт лучшие фрагменты и пишет по
ним ответ как бы то ни было. Если фрагменты нерелевантны, модель всё
равно пишет уверенный текст — и это худший вид отказа, потому что
снаружи он неотличим от правильного ответа.

Оценка идёт по сигналам, которые уже есть в поиске, без обращения к
модели (иначе каждый вопрос стал бы ещё дороже):

| Балл | Решение |
|---|---|
| ≥ 0,55 | отвечать |
| 0,30–0,55 | один раз переформулировать запрос и искать шире, без доменного фильтра |
| < 0,30 | спросить роутера, не другой ли домен, иначе честно отказаться |

Дальше отказа отвечает **граф ссылок** (см. ниже). Штраф за сужение
на одном документе попадает и в решение, и в метрики — иначе экипаж
сравнивал бы две попытки поиска от разных чисел.

### Агентная — десять агентов и выбор инструмента

Роутер выбирает домен **и режим**: `documents`, `metrics` или `both`.
Специалисты по доменам, сводный аналитик, аналитик витрины, критик.

Решение роутера считается подсказкой. Если вопрос просит разбивку или
динамику (`по факультетам`, `динамика`, `за год`, `больше всех`) и
метрика в витрине находится, числа добавляются в любом случае.
Наблюдение из живого прогона: на вопрос «покажи отчисления по
факультетам» роутер на модели 1.5b выбрал документы, и агент честно
ответил, что в документах таких данных нет — они есть только в
витрине. Формально он был прав, ректору это не помогло.

### Инструмент чисел

`tools.py`: по синонимам метрик и стеммеру находит показатель и
подразделение, строит параметризованный `SELECT` по `fact_metric` и
возвращает значение, период, разбивку по подразделениям и динамику.

Пользовательский вопрос **не попадает в текст SQL ни одним символом** —
он используется только для подбора метрики и подразделения, значения
подставляются параметрами. Список таблиц и полей зашит в код.

Каждое число подписано источником — документом университета или
карточкой мониторинга. Метку источника ставит **код**, а не просьба
модели: если положиться только на инструкцию в промпте, при неудачном
запросе подпись потеряется и ответ будет выглядеть как отчётные данные.

### Граф ссылок вместо полного GraphRAG

Полноценный GraphRAG — это извлечение сущностей и связей моделью плюс
сводки кластеров. На 1.5b без видеокарты это минуты на документ: при
сотне документов индексация растянется на часы, а извлечение сущностей
на такой модели даёт мусор. Система станет работать хуже нынешней.

Нужный сбой у корпуса вуза другой и детерминированный: положение
утверждено приказом, протокол ссылается на положение, отчёт ссылается
на протокол. Эти связи берутся регулярками за секунды.

`graph.py`: узлы — документ, раздел, приказ, протокол; связи —
`contains`, `part_of`, `mentions`. Вопрос → опознание номера или
названия → обход на 1–2 прыжка → добор фрагментов соседних документов
с пометкой «найдено по связям».

Две тонкости, на которые ушла часть времени:

- **схема `№ N` без слова «приказ» или «протокол» использовать нельзя.**
  Она превращала «приказ № 214-р» ещё и в «протокол № 214», и в графе
  появлялись узлы-призраки, по которым потом шёл обход и приводил к
  «найденным» документам, которых там нет;
- **названия документов сравниваются по основам слов**, а не по сырым
  словам: «положении» из вопроса и «положение» из названия подстроками
  друг друга не содержат, и документ не находился ни при каком числе
  совпадений.

Граф строится автоматически при каждой индексации.

### Мультимодальность — таблицы и честные пробелы

`extract.py` разбирает PDF постранично:

- таблицы достаются и кладутся в текст как markdown — так же, как уже
  делалось для XLSX, и строка ячейки остаётся строкой для эмбеддинга;
- страница с изображением и коротким текстом помечается как графическая,
  и **в текст вносится явная метка**, которую видит модель.

Без этой метки система молчала бы о графике, а потом уверенно
говорила «в документе про это ничего нет» — хотя на странице схема.
Намеренно показанные сведения о страницах хранятся в таблице `doc_page`.

Чего здесь нет и почему:

- **OCR для сканов** (Tesseract, PaddleOCR) — выключен по умолчанию и
  требует отдельной установки. «Найденные» с распознанного отскана
  номера документов без проверки опаснее, чем честное «не извлечено»;
- **CLIP / ColPali** — недоступны без видеокарты, а не притворяются
  работающими. На машине с видеокартой это включаемая опция;
- **неразобранный общий шаблон `№ N`** — сознательно удалён, см. выше.

Проверка `backend/tests/test_pdf_tables.py` собирает настоящий PDF с
таблицей и страницей-картинкой и убеждается, что всё это читается.

### Проверка ответа на выдуманные числа

Просьба «не придумывай» в промпте не работает на модели 1.5B: на вопрос
об итогах успеваемости она ответила «У — от 35 % до 45 %, СБ — 85», хотя
таких чисел в документе нет. Поэтому ответ проверяется после генерации
(`backend/grounding.py`):

- числа из ответа сверяются с числами тех фрагментов, что реально ушли
  модели; предложение с неподтверждённым числом удаляется целиком;
- ссылки `[n]` проверяются на диапазон — на несуществующий фрагмент
  снимаются;
- повторы одного и того же пункта схлопываются: 1.5B уходит в цикл и
  повторяет пункт десяток раз;
- если после чистки ничего не осталось, показываются найденные
  фрагменты и причина, а не пустой ответ.

Отчёт проверки печатается под ответом («убрано предложений…, числа…»)
и лежит в `meta.grounding`. Отключается `RECTOR_STRICT_NUMBERS=0` —
только для отладки. Проверки: `backend/tests/test_grounding.py`.

## Агенты

Ответ в интерфейсе готовит **один вызов модели**: поиск по документам,
затем один ответ. Переключатель «Экипаж / Один агент» из интерфейса
убран, потому что он обещал неправду — в режиме «fast» пропускался
только критик, а роутер и аналитик витрины работали в обоих режимах.

Экипаж агентов (ниже) остаётся доступен как `/api/ask/crew` — это
«глубокий разбор», до четырёх обращений к модели подряд. На машине без
GPU он занимает десятки минут, поэтому по умолчанию чат им не
пользуется: человек получал ошибку вместо ответа.

```
чат:    вопрос → поиск по документам → один ответ модели

экипаж: вопрос → роутер → [числа из витрины] → [поиск + оценка контекста]
              → специалист → критик (не всегда) → (одна правка)
```

| Агент | Что делает |
|---|---|
| Роутер | Определяет домен и тип вопроса. Ответ не даёт |
| Планировщик | Решает, нужен ли критик, и объясняет решение |
| Специалист по контингенту | приём, численность, отчисления |
| Специалист по успеваемости | успеваемость, задолженность, аттестация ППС |
| Специалист по финансово-хозяйственной деятельности | доходы, расходы, ФОТ, план ФХД |
| Специалист по качеству образования | ВНОКО: опросы, план-факт, ВПР |
| Специалист по воспитательной работе | студсовет, юридическая клиника, карьера |
| Специалист по науке | гранты, публикации, патенты |
| Специалист по цифровым сервисам | ЭИОС, LMS, нагрузка ППС, аудитории |
| Сводный аналитик | вопросы вне одного домена |
| Аналитик витрины | считает по витрине и отвечает числами |
| Критик | проверяет ответ по фрагментам |

**Как решается, сколько агентов нужно.** Критик — отдельный вызов
модели, на этой машине это десятки секунд. Платить ими за простой факт
(«сколько обучающихся») незачем: там, где ответ — цифра из документа,
проверять нечего, а ректор ждать не готов. Критик зовётся там, где
ответ собирается из нескольких источников или требует объяснения:
тип вопроса `explain` или `report`, режим «числа и документы», вопрос со
сравнением или разбором. Решение видно в следе работы, и «ответ проверен
критиком» пишется только когда критик действительно работал.

**Роутер сначала считает сам.** Домен выводится из показателя, который
нашёлся в витрине: у показателя известен блок, а у блока — специалист.
Это быстрее и надёжнее угадывания по синонимам. Модель к роутеру
обращается только тогда, когда по словам домен определить не удалось:
на вопрос «сколько всего обучающихся» локальная модель отвечала
«ДОМЕН: 123456», и вопрос уходил в сводного аналитика.

**Что от этого реально меняется, а не просто выглядит умнее.**

- **Специалисты видят разные документы.** Каждому соответствует блок
  дашборда, привязка хранится в таблице `doc_block`. Агент по финансам
  физически не получает положение о приёме. Без этого все десять были бы
  одним и тем же агентом с разным именем.
- **У специалистов разные требования к ответу.** Финансист обязан
  назвать период и единицу измерения, академик — отличать витрину
  дашборда от фактов из документов, специалист по науке не должен
  складывать Scopus и РИНЦ в одно число. Общие требования (только по
  источникам, ссылка, «не найдено») вынесены в базу и не размываются.
- **Критик — отдельный вызов модели со своим контекстом.** Он не видит
  рассуждений автора, только фрагменты и готовый текст. Просить модель в
  том же контексте «проверь себя» бессмысленно: она продолжает исходные
  посылки и подтверждает саму себя.
- **Неразобранный вердикт не считается «всё хорошо».** Иначе проверку
  можно обойти, просто ответив не по формату.

**Чего экипаж не делает.**

- Не вызывает всех девять подряд: работает только один специалист,
  выбранный роутером. Три вызова модели на вопрос.
- Не крутит цикл правок: замечание критика даёт ровно одну попытку.
  Иначе на слабой модели система будет крутиться до таймаута.
- Не притворяется, что отработал. Если модель недоступна, в ответе
  будет написано, какие агенты не сработали и почему, а в ходе работы
  появится неуспешный шаг.

**Сколько это стоит по времени.** Полный цикл — три-четыре обращения к
модели подряд. На процессоре без видеокарты это минута и больше, поэтому
есть режим «Один агент»: он же служит запасным путём при отказе экипажа.
Под ответом раскрывается весь ход работы с именами агентов, временем
каждого шага и вердиктом критика.

### Как документ попадает к специалисту

Таблица `doc_block` связывает документ с одним или несколькими блоками.
Порядок определения:

1. Метка в самом файле (frontmatter markdown):
   ```
   ---
   blocks: finance, results
   ---
   ```
2. Ключевые слова в названии файла и заголовке документа.
3. Ключевые слова в начале текста — с ограничением по числу блоков.

Протокол учёного совета и стратегия относятся сразу к нескольким блокам:
одного блока на документ тут не хватает, иначе пришлось бы либо терять
документ, либо показывать его всем подряд.

Сколько документов видит каждый специалист — видно в `GET /api/agents`.
Агент с нулём документов в интерфейсе выглядит как пустая обёртка, и это
лучше, чем молча отвечающий по чужой теме.

## Как работает поиск

Вопрос проходит три стадии:

1. **По словам** (FTS5). Название, заголовок и текст куска. Запрос
   стеммируется по-русски: «отсев» находит «отчисления».
2. **По смыслу** (векторы). Вопрос кодируется той же моделью, что и
   документы, и сравнивается с кусками.
3. **Слияние RRF** + переранжирование. Результаты двух каналов
   объединяются по рангам, затем пересортировываются по тому, какая
   доля вопроса попала в название документа, заголовок и текст.

Три решения, без которых качество падает:

- **Каналы обрезаются до одинаковой длины до слияния.** Иначе канал,
  вернувший больше записей, выигрывает сам по себе за счёт количества
  и топит точные совпадения другого.
- **Канал-вектор отключается, если модель не скачана.** Эмбеддинг-заглушка
  не несёт смысла; если дать ему половину веса, он перемешает выдачу.
  Система пишет об этом в `/api/health` и в ответе — молча деградировать
  нельзя.
- **Совпадение в названии важнее совпадения в абзаце.** На вопрос про
  аттестацию регламент об отчислениях выигрывал за счёт слов
  «аттестация» и «преподаватель», хотя правильный документ содержал
  только первое — зато в самом названии.

## Локальная модель

Работает через Ollama, без интернета и без облака. Модель выбирается
автоматически: `backend/autoconfig.py` спрашивает Ollama, какие модели
скачаны, и берёт лучшую из установленных. Список в `config.py` — запасной
вариант для машины, где ещё ничего не скачано.

```
ollama pull qwen2.5:1.5b        языковая модель
ollama pull nomic-embed-text     модель эмбеддингов (или bge-m3)
```

**Почему qwen2.5, а не qwen3.** Модели семейства qwen3 (например,
`qvikhr`) дают ответы точнее, но на задачах с жёстким форматом уходят
в размышление: на тесте роутера `qvikhr` отработал 306 секунд и
проигнорировал ограничение длины ответа в 60 токенов. У qwen2.5 режима
размышления нет, поэтому время ответа предсказуемо: 5 секунд на
роутер, 15–20 на ответ специалиста. Если на вашей машине есть
свободная память и вы готовы ждать — можно выбрать qwen3 вручную.

**Модель эмбеддингов менять нельзя, пока в базе есть векторы.** Они
посчитаны конкретной моделью, у неё своя размерность. Смена модели без
пересчёта корпуса сделает поиск молча неправильным. `autoconfig`
поэтому оставляет прежнюю модель, если векторы уже посчитаны.

### Сколько занимает ответ

| Вопрос | Агентов | Время на этой машине |
|---|---|---|
| «сколько обучающихся» | роутер, специалист | 10–25 с |
| «почему важно оценивать трудоустройство» | + критик | 60–220 с |

Пока модель думает, в панели ассистента видно, что идёт работа. Если
вопрос отправлен повторно, потому что «зависло», — ответ придёт дважды;
это цена локальной модели на процессоре без видеокарты.

## Что делать, если ИИ молчит

Ассистент всегда объясняет, что с ним не так. Три частые причины:

**`Ollama не отвечает`** — не установлена или не запущена.
Установите с <https://ollama.com>, затем запустите `start.bat`.

**`модель ... не скачана`** — выполните в терминале:
```
ollama pull qwen2.5:1.5b
ollama pull nomic-embed-text
```
Модель выбирается автоматически под ваш компьютер, `install.bat`
печатает, какая именно.

**`векторы в аварийном режиме`** — корпус проиндексирован с заглушкой
(например, при первой установке без интернета). После скачивания
модели пересоберите индекс:
```
.venv\Scripts\python.exe -m backend.ingest --force
```
До этого поиск работает только по словам — это заметно хуже, но
работает.

### Как поставить модель мощнее

Модель по умолчанию выбирается по железу при установке. Поменять её
потом можно одной командой — переустанавливать ничего не нужно:

```
.venv\Scripts\python.exe -m backend.models                 что сейчас
.venv\Scripts\python.exe -m backend.models list            что скачано
.venv\Scripts\python.exe -m backend.models small vikhr-7b:latest
.venv\Scripts\python.exe -m backend.models large qwen2.5:14b
.venv\Scripts\python.exe -m backend.models auto small      вернуть автовыбор
```

Что важно знать:

- Сервер подхватывает смену **без перезапуска**: модель читается из
  базы на каждом вопросе.
- Индекс пересчитывать **не нужно** — он зависит от модели эмбеддингов,
  а не от языковой.
- Команда проверяет, что модель скачана. Если её нет — покажет
  `ollama pull` и похожие теги; записать нескачанную можно только с
  `--force`.
- Большие модели на процессоре отвечают минутами. Если появляется
  `ошибка обращения к Ollama: timed out` — поднимите
  `RECTOR_OLLAMA_TIMEOUT` (по умолчанию 300 с), например до 900.
- Переменные `MODEL_SMALL` / `MODEL_LARGE` сильнее базы: если они
  заданы, команда меняет базу, но работать будет переменная. Команда
  об этом предупреждает.
- 7B и больше имеет смысл ставить на машине с 16 ГБ ОЗУ и выше.
  На ноутбуке с 8 ГБ ответов не будет быстрее — только дольше.

### Публикационная активность (платформа «Доступ»)

Снимок лежит в `data/science_publications.json` и отдаётся через

метакомпетенции». Платформа работает в вузовской сети
(`http://10.19.20.20:8080/`); пароль в репозитории не хранится.

Онлайн-обновление включается переменными окружения:

| Переменная | Смысл |
|---|---|
| `SCIENCE_API_URL` | JSON-адрес платформы, например `http://10.19.20.20:8080/api/science` |

Ответ API должен содержать `publications_total` (или

угадывает и показывает последний снимок. РИНЦ и Scopus не
суммируются — это разные учёты.

## Ограничения, о которых надо знать

- **Цифры ленты — из документов.** Новые значения попадают в
  `fact_metric` через загрузчик и подтверждение на экране проверки.
- **Состав программ и подразделения — реальные, цифры — из документов.**
  Коды ФГОС, годы их редакций и названия кафедр взяты с сайта
  университета. Численность обучающихся по программам на сайте не
  публикуется, поэтому в справочнике её нет: вымышленные числа ректор
  принял бы за данные.
- **Персональные данные.** Drill-down с ФИО остался от прежней
  демонстрационной витрины; при загрузке настоящих данных персональные
  данные нельзя класть в базу без обезличивания (152-ФЗ): для этого в
  `fact_detail` заведена колонка `subject_hash`.
- **Репозиторий должен быть приватным** — в `knowledge/` попадают
  положения и протоколы вуза.
- **Модель скачивается один раз при установке** — нужен интернет.
  Если на компьютере ректора интернета нет, модель переносится
  файлом с машины, где есть.
- **PDF собирается печатью браузера.** В `style.css` есть блок
  `@media print`, который собирает из дашборда отчёт на A4: все три
  представления, без теней и интерактивных элементов, с сохранением
  цветов статусов. Кнопка «PDF» открывает диалог печати — выбираете
  «Сохранить как PDF». Нативный генератор PDF нужен только если файл
  требуется без диалога.
- **Скриншот печати в проверке не снимался.** В браузере теста нет
  инструмента печати, а снимок экрана требует видимого окна на
  рабочем столе. Поэтому печать проверена функционально: правила
  распакованы из `@media print` и внедрены в живую страницу, после чего
  измерены вычисленные стили — все три представления показываются,
  интерактивные элементы и кнопки скрыты, шапка статична, фон белый,
  сетка карточек две колонки. Визуально напечатанный лист не
  проверялся.
- **Перенос из чужого репозитория ограничен приёмами, а не кодом.**
