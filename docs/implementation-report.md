## 1. Краткий итог

Конвейер из ТЗ 2.0 собран целиком: **файл → извлечение → разбор малой
моделью → детерминированные проверки → объяснение большой моделью →
экран проверки → явное подтверждение → публикация с провенансом**.

Что изменилось по сравнению с исходным состоянием:

- **Публикация перенесена из приёма файла в решение человека.** Раньше
  `confirmed=true` в анкете сразу писал числа в витрину; теперь загрузка
  всегда становится `needs_review`, а числа попадают в витрину только
  после кнопки «Принять» на экране проверки — в одной транзакции с
  провенансом.
- **Новый контур данных** (8 таблиц): сырье файла с адресами ячеек,
  parse card, проверки, решения человека, провенанс, журнал, лимит попыток
  входа, трасса вызовов модели.
- **14 детерминированных проверок** (суммы, дубли, аномалии ×3, ссылки на
  источник, периоды) с делением на блокирующие ошибки и предупреждения.
- **Две роли моделей** с честным отказом: без большой модели экран проверки
  пишет причину, а не подставляет другую; вся модельная работа пишется в
  `llm_trace`.
- **Безопасность:** Argon2 с переходом со старых хэшей, лимит попыток входа,
  CSRF-проверка Origin, журнал событий с CSV-выгрузкой.
- **Интерфейс:** новый экран проверки (`review.html`), статусы и ссылки в
  списке загрузок, журнал, провенанс числа в детализации показателя.

Проверено: **48 тестов проходят** (было 36), сквозной HTTP-прогон на копии
боевой базы — **0 провалов**, включая приём файла с настоящей моделью
(46.4 с) и публикацию с провенансом. Боевой сервер перезапущен на новом
коде.

Что осталось за рамками — только по решению владельца: подключение большой
модели при размещении на ВМ, вердикт по лимиту входа и по открытых
read-only маршрутов (§11).

## 4. Миграции БД и обратная совместимость

Все изменения — **аддитивные**: новые таблицы и колонки, ни одной перезаписи
значений, ни одного `DROP`. Существующие данные (417 строк `fact_metric`,
47 метрик каталога, 2 старые загрузки) не изменялись.

Новые таблицы: `upload_raw`, `parse_card`, `upload_check`, `upload_decision`,
`fact_provenance`, `audit_log`, `login_attempt`, `llm_trace`.
Все восемь есть в боевой базе — проверка `PRAGMA table_info` после миграции.

Новые колонки (добавляет `_migrate` через `ALTER TABLE`):

- `upload`: `original_name`, `mime_detected`, `extension`, `uploaded_by`,
  `note`, `error_code`, `error_message`, `parsed_at`, `decided_at`
  (старые строки `upload` получают NULL — читающий код показывает `filename`);
- `fact_metric`: `value_exact TEXT` — каноническая десятичная строка.
  **У старых 417 строк колонка осталась NULL**: источником истины для них
  остаётся `value REAL`, и читающий код это учитывает
  (`ex.get("value_exact") or ex.get("value")`), витрина читает как раньше `value`;
- `dim_metric`: `min_val`, `max_val`, `tolerance`, `periodicity`
  (NULL = диапазон не задан, проверка не выполняется);
- `parse_card`: `explanation`, `expl_model`, `expl_ms`, `explained_at` —
  кэш объяснения большой моделью.

**Фактический прогон миграции** (команда `python stage4_migrate_real.py`,
копирует то же действие, которое делает `db.init_db()` при импорте `app.py`):

```
fact_metric до/после: 417 417
parse_card: upload_id, doc_type, division_id, period, period_id, values_json,
  mapping_json, unmapped_json, status, confidence, model, attempts, parse_ms,
  parse_error, edited_at, edited_by, explanation, expl_model, expl_ms, explained_at
dim_metric: metric_id, block_id, title, unit, dir, target, ord, source, src_note,
  min_val, max_val, tolerance, periodicity
строк upload: 2   строк upload_raw: 0   строк fact_provenance: 0
```

Сверка схемы (команда `python stage4_schema_diff.py`, схема из кода против
боевой базы): `таблиц в реальной базе: 35 | в схеме: 33`, `нет в реальной: нет`,
`результат: схемы совпадают`. Две «лишние» таблицы — `graph_edge`, `graph_node`,
старые таблицы прежней функции, к ТЗ не относятся, не удалялись.

Найденные и исправленные дефекты миграции (см. §11):

1. Колонки `parse_card.explanation` были в `SCHEMA`, но отсутствовали в
   `_migrate`: база, где `parse_card` создалась раньше, получила бы
   «no such column» на первом же сохранении объяснения. Добавлены в `_migrate`.
2. Колонки диапазонов `dim_metric` числились в миграции, но в боевой базе их
   не оказалось — миграция после их добавления на боевую базу не выполнялась.
   Выполнена, сверка выше.
3. `_migrate` падал целиком, если в базе нет одной из перечисленных таблиц:
   `ALTER` по несуществующей таблице обрывал оставшиеся правки. Добавлена
   проверка `sqlite_master`.

Параметры базы: `PRAGMA journal_mode = wal` (был и раньше),
`PRAGMA busy_timeout = 5000` (добавлен — без него параллельный запрос
и загрузка при WAL падали сразу), `PRAGMA foreign_keys = ON`
(выставляется в `db.connect()`, это свойство соединения, а не базы).

## 5. Реализованные API и UI

### 5.1 HTTP-маршруты

Всего в `backend/app.py` — **23 маршрута** (`@app.get`/`@app.post`).
Новые по ТЗ 2.0:

| Метод и путь | Назначение | Доступ |
|---|---|---|
| `GET /api/upload/{id}/review` | состояние загрузки для экрана проверки: анкета, parse card, проверки, конфликты, заменяемые значения, сырьё, объяснение, решения | своё подразделение или admin, иначе 401/403/404 |
| `GET /api/upload/{id}/raw?offset&limit` | страница сырья документа (`items`, `total`, `offset`, `limit`) | то же |
| `POST /api/upload/{id}/decide` | решение человека: `accept` (публикация), `fix` (сохранить правки), `reject` | то же |
| `POST /api/upload/{id}/explain` | объяснение проверок большой моделью (с кэшем) | то же |
| `GET /api/journal`, `GET /api/journal/export/csv` | журнал событий и его выгрузка, фильтры `action`, `actor`, `limit`, `offset` | только с сессией |
| `GET /api/metrics/{id}/sources` | провенанс значений показателя: период, точное значение, файл, подразделение, способ извлечения, модель, кем и когда подтверждено | без сессии — как витрина и `export/xlsx` (см. ниже) |

Изменённые:

- `POST /api/upload` — **не публикует**. Возвращает `status:"needs_review"`,
  число ошибок/предупреждений проверок, карточку разбора и `review_url`;
  дубликат — `{"duplicate":true}`; фальшивый формат — 415; пустая анкета — 400.
- `GET /api/uploads`, `GET /api/uploads/{id}` — поля `original_name`, `status`,
  `errors`, `warnings`, `freshness`; выборка по подразделению не расширяется
  параметром клиента.
- `GET /api/health` — без путей сервера, плюс `roles` (small/large: модель,
  `installed`, `resolved`, `fallback`).
- `POST /api/login` — лимит попыток (429) и журнал `login`/`login_fail`/`login_block`.
- `POST /api/reindex`, `GET /api/export/xlsx` — пишут журнал `reindex`/`export`.

Коды ошибок экрана проверки (`409`): `blocking` (блокирующие ошибки проверок),
`conflict` (перезапись значений — клиент подтверждает список `overwrite`),
`no_period` (период не определён), `duplicate`, `bad_period`.

Замечание по доступу: `GET /api/metrics/{id}/sources` не требует сессии —
иначе перестал бы работать drill-down на открытом без входа экране витрины.
Так устроены и `/api/metrics`, и `/api/export/xlsx` (владелец оставил эти
read-only маршруты открытыми). Вместе с тем этот маршрут отдаёт имя
исходного файла и подразделение — **список открытых маршрутов стоит
пересмотреть владельцу перед размещением на ВМ** (см. §11).

### 5.2 Интерфейс

**`web/review.html` + `web/js/review.js` — экран проверки** (главный экран
по ТЗ §10). Восемь блоков в стиле дизайн-системы (`section-card`/`card-head`,
токены CSS, без внешних ресурсов):

1. **Загрузка** — исходное имя файла, размер, время, кто загрузил,
   подразделение, тип, sha256 (моноширинный, обрезан, полный в `title`),
   статус (перевод: `needs_review` → «Ждёт проверки», `accepted` →
   «Опубликовано», `rejected` → «Отклонено», `failed` → «Ошибка»).
2. **Анкета** — что за данные, период, частота, ответственный, уровень доступа.
3. **Карточка разбора** — таблица сопоставлений: показатель, единица,
   редактируемое значение, источник («из анкеты» / «нашла модель» с подписью
   «модель: X» при расхождении), привязка к строке сырья; «Добавить строку»
   (показатель из каталога), удаление строки, «Не сопоставлено», поля
   «Тип документа» и «Период» (+ `<datalist>` из периодов витрины).
4. **Проверки** — счётчик «Ошибок / Предупреждений», ошибки с меткой
   «блокирует».
5. **Объяснение ИИ** — текст либо честная причина недоступности + кнопка
   «Запросить объяснение».
6. **Конфликты** — чекбоксы перезаписи (по умолчанию отмечены → уходят
   в `overwrite`), приписка «Будут заменены…».
7. **Сырьё документа** — метка строки/ячейки и её текст, «Показать ещё»
   через `GET .../raw?offset=&limit=300`.
8. **Решение** — комментарий и три кнопки; при `status !== needs_review`
   выключены («Загрузка уже решена»).

Клиентские правила: `fix` и неудачный `accept` перечитывают состояние;
`409 blocking` → красное сообщение и повторный GET; `409 conflict` →
перерисовка чекбоксов и **один** авто-повтор с `overwrite` (дальше — просьба
подтвердить вручную, защита от зацикливания); `409 no_period` → фокус на
поле периода; `reject` — с `confirm()`. Всё экранируется `esc()`.

**`web/upload.html`** — после приёма показывает: имя файла, куски в индексе,
счётчик ошибок/предупреждений проверок и главное — «Файл принят, но числа
ещё не опубликованы» + кнопка «Проверить и подтвердить → `review.html?id=N`»;
для дубля — отдельный текст и ссылка на проверку существующей загрузки.
Вывод путей сервера убран, `accept` дополнен `.csv`.

**`web/uploads.html`** — колонка «Статус» с переводом статусов, бейджи
`⚠ N` / `✖ N` (только ненулевые) и ссылка «Открыть» на `review.html?id=N`
(в том числе для старых загрузок со статусом `ok`, у которых разбора нет,
но карточка открыта).

**`web/journal.html`** — журнал событий: фильтр по событию (выпадающий
список всех типов записей) и по логину, «Показать ещё 50», кнопка
«Выгрузить CSV» → `/api/journal/export/csv`. Страница открывается только
под сессией; без неё — форма входа с обработкой 429.

**`web/js/app.js`** — в детализации показателя добавлен блок
«Провенанс числа»: `/api/metrics/{id}/sources` рисует таблицу
«период · значение · документ · подразделение · как извлечено · подтвердил».
Если значений из документов нет — честный текст про демо/ручные числа.

## 6. Меры безопасности

Реализация по ТЗ §12, §14, §17. Проверено фактическими запросами (§9).

| Мера | Как сделано | Проверка |
|---|---|---|
| Вход по логину | cookie `dashboard_session`, `HttpOnly`, `SameSite=Lax`, TTL 8 ч | 200 при верном пароле, 401 при неверном |
| Пароли | **Argon2id** (`argon2-cffi 25.1.0`); старые PBKDF2-хэши хранятся как есть и **автоматически пересчитываются в Argon2 при первом успешном входе** | после входа `pass_hash` начинается с `$argon2`, повторный вход работает |
| Лимит попыток входа | счётчик неудач за окно (`LOGIN_WINDOW_MIN`), при `LOGIN_MAX_ATTEMPTS` — блок **429** с объяснением; включён по умолчанию, `RECTOR_LOGIN_LIMIT=0` отключает | 5 неудач → следующая попытка 429 «…заблокирован…» |
| CSRF | middleware проверяет `Origin`/`Referer` у небезопасных методов; запрос без Origin (curl, скрипт) пропускается, а чужой Origin — нет; запись о чужом Origin попадает в журнал | `POST /api/logout` c `Origin: http://evil.example` → **403**, сессия после этого цела (`/api/me` → 200) |
| Доступ к данным | маршруты проверяют подразделение по сессии; параметр клиента не расширяет выборку | чужая загрузка → **403**; `/api/me`, `/api/upload/{id}/review`, `/api/upload/{id}/decide`, `/api/journal` без сессии → **401** |
| Журнал событий | `backend/journal.py`: вход, неудачный вход, блокировка, выход, загрузка, дубликат, решение, публикация, переиндексация, выгрузка | `/api/journal` без сессии → 401; в журнале есть `login`, `upload`, `publish` |
| Выгрузка CSV | экранирование формул (`=`, `+`, `-`, `@`, кавычки) — защита от инъекции при открытии в Excel | CSV открывается, `publish` присутствует, заголовок `id,ts,actor,...` |
| Пути сервера не утекают | `health` отдаёт только состояние (`ОК/нет/др.`) и роли моделей — без путей базы и `knowledge`; тексты ошибок — коды + объяснение без путей | в ответе health нет ключей `database` и `knowledge_dir` |
| Файлы | лимит размера `MAX_UPLOAD_MB` по потоку (вся файла в память не читается), магические байты против расширения, защита от zip-бомбы, на сервере имя = uuid (оригинал — в `upload.original_name`) | подмена `.pdf` текстом → 415, повтор того же файла → дубликат |
| Форматы | `.docx`, `.xlsx`, `.csv`, `.pdf`, `.txt/.md`, **`.xls`** (через установленный `xlrd`); **`.doc` отклоняется** с инструкцией «сохранить как .docx» | 415 с текстом инструкции |

Конфликт с прежним решением владельца: раннее решение — «лимита входа нет»
(оставлено текстом в старых материалах), ТЗ 2.0 §12 требует лимит. Сделано по
ТЗ: лимит включён по умолчанию, отключается `RECTOR_LOGIN_LIMIT=0`.
**Нужно решение владельца** — какой вариант считать окончательным.

Открытые read-only маршруты владельца сохранены без сессии:
`/api/health`, `/api/ask`, `/api/export/xlsx`, `/api/reindex`, `/api/docs`
(предупреждение о доступе выводится в интерфейсе).

## 7. Конфигурация моделей и трассировка

Роли моделей (ТЗ §13): `small` — разбор документов (parse card), `large` —
объяснения проверок. Разрешение роли: `MODEL_SMALL`/`MODEL_LARGE` из окружения →
значение в `meta` базы → кандидат из `config.MODELS_*`.

Фактическое состояние на машине (ответ `/api/health`, роли):

```json
"small": {"model": "qwen2.5:1.5b", "installed": true,  "resolved": "meta", "fallback": false}
"large": {"model": "qwen2.5:14b",  "installed": false, "resolved": "auto", "fallback": false}
```

Правила, которые соблюдаются буквально:

- **отсутствие модели — честный отказ.** Если запрошенной роли нет,
  вызов возвращается с точной причиной (`model_available` проверяет точный
  тег модели), без молчаливой подмены на другую. Объяснение в интерфейсе
  отвечает: `{"available": false, "reason": "большая модель qwen2.5:14b не
  подключена (подключается при размещении на ВМ)"}`.
- **большая модель подключается при размещении на ВМ** — до тех пор
  `large` честно недоступна.
- `RECTOR_LARGE_FALLBACK=1` — явный фолбэк объяснений на малую модель;
  по умолчанию выключен, включается переменной окружения.
- Больше модель не подменяется: `resolve_role` при пустом теге не выдаёт
  случайную модель из списка.

Трассировка: каждая модельная операция пишется в `llm_trace`
(`ts, purpose, role, model, resolved, duration_ms, ok, error_code,
prompt_chars, response_chars`) — `chat` с ролью и `answer` (purpose=`ask`).
Ошибки кодируются отдельно: `ollama_down`, `model_missing`, `http_<code>`,
`transport`, `empty`. Запись трассы не роняет вызывающего: исключение
в ней проглатывается, вызывающий получает свой результат.

Отдельно пишется `parse_card.parse_ms` и `attempts` (сколько раз модель
пыталась выдать валидный JSON — максимум два) — это видно на экране проверки.

## 11. Ограничения и невыполненные критерии

### Ограничения, снятые договорённостью с заказчиком

1. **Большая модель не подключена.** На машине её нет, подключение — при
   размещении на ВМ. Экран проверки показывает честную причину; весь путь
   «роль → модель → вызов → кэш → трасса» проверен с `MODEL_LARGE=qwen2.5:1.5b`
   (см. §9.2). Качество текста объяснения на малой модели слабое — оценивать
   его нужно будет на большой.
2. **`.doc` (Word 97) не читается** — формат отклоняется с инструкцией
   «пересохраните как .docx». Читаемые форматы: `.docx`, `.xlsx`, `.xls`,
   `.pdf`, `.csv`, `.txt`, `.md`.
3. **Фонового статуса загрузки нет**: приём идёт синхронным запросом
   45–60 с и выглядит в браузере как «повисло». Прогресс-бар и разбиение
   на шаги — отдельная задача.

### Вопросы, которые должен решить владелец

4. **Лимит попыток входа.** ТЗ 2.0 §12 требует, раннее решение владельца —
   «лимита нет». Сделано по ТЗ (включён по умолчанию, выключается
   `RECTOR_LOGIN_LIMIT=0`) — нужен вердикт, какой вариант окончательный.
5. **Открытые маршруты.** Без сессии работают `/api/health`, `/api/ask`,

При старте `app.py` вызывает `db.init_db()`: `SCHEMA` + миграции + индексы.
Ручной эквивалент (использован в этой работе): `python stage4_migrate_real.py`.

Переменные окружения, которые имеют значение для ТЗ 2.0:

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `MODEL_SMALL`, `MODEL_LARGE` | теги моделей ролей (приоритет над `meta`) | из `meta`/конфига |
| `RECTOR_LARGE_FALLBACK=1` | объяснения большой модели считает малая | выключено |
| `RECTOR_LOGIN_LIMIT=0` | отключить лимит попыток входа | лимит включён |

| `RECTOR_MAX_UPLOAD_MB` | лимит размера файла (потоковый) | 50 |
| `RECTOR_MAX_RAW_ROWS` | сколько строк сырья хранить | 6000 |
| `RECTOR_SUM_TOLERANCE` | допуск суммы | 0.01 |
| `RECTOR_OLLAMA_URL`, `RECTOR_OLLAMA_TIMEOUT` | адрес и таймаут Ollama | `http://127.0.0.1:11434` / 300 с |
| `RECTOR_API_PORT` | порт сервера | 8765 |

### Резервное копирование

`backup.bat` копирует `data/dashboard.db` (при работающем сервере — учитывать
WAL: журнал `-wal`/`-shm` должен уезжать вместе с основным файлом либо
копия делается с остановленным сервером). Папка `knowledge/` содержит
исходные документы — её бэкап делается средствами файловой системы отдельно,
она в резервную копию по умолчанию не входит.

### Восстановление

База восстанавливается подстановкой файла `data/dashboard.db`; миграции
идемпотентны (проверка по `PRAGMA table_info`, ALTER выполняется один раз),
старая база поднимается под текущий код. Схема после восстановления сверяется
командой `python stage4_schema_diff.py`.
