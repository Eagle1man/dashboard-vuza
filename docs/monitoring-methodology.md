# Методика мониторинга: что взяли из статьи и что уже сделано

Источник: Самарина О. В., Самарин В. А. «Разработка системы мониторинга
ключевых показателей деятельности университета» // Вестник Югорского
государственного университета, 2025, т. 21, вып. 4. DOI
10.18822/byusu20250499-106.

Статья описывает опыт Югорского госуниверситета: переход от разрозненных
отчётов к управлению на данных через многоуровневые дашборды.

## Рекомендации статьи и наша реализация

| Рекомендация | У нас |
|---|---|
| Три уровня панелей: стратегический, операционный, аналитический | Обзор (стратегический), лента показателей (операционный), мониторинг и детализация блока (аналитический) |
| Единое хранилище вместо отчётов по подразделениям | SQLite-витрина `fact_metric` + провенанс `fact_provenance` |
| Показатель без источника не считается отчётным | Публикация только через `/review.html`, число без провенанса не попадает в витрину |
| Автоматизация сбора вместо ручных выгрузок | Загрузка файла + разбор + карточка; мониторинг тянется скриптом с сайта |
| Импортозамещение платформ (Loginom, Visiology) | Свой интерфейс на локальных библиотеках, без внешних CDN и облаков |
| Поэтапное расширение метрик | Сначала витрина вуза, затем мониторинг ВО, затем СПО |

## Чего в статье нет, а нам нужно

- **Проверка чисел.** У них акцент на визуализации, у нас — на
  `grounding.py`: ответ с числом, которого нет в найденных фрагментах,
  снимается.
- **Сравнение с другими вузами.** Статья про внутренние KPI; мы добавили
  внешний контур — места среди вузов и организаций СПО Ростовской
  области.
- **Ограничение по железу.** Их стек предполагает серверы с GPU; наш
  работает на CPU без AVX2, поэтому модели малы, а ответы медленнее.

Вывод: архитектурные принципы статьи совпадают с тем, что уже собрано;
добавлять тяжёлую BI-платформу смысла нет — не хватает не визуализации,
а скорости моделей и качества данных.
